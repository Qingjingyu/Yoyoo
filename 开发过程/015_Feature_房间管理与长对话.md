# 015 Feature: 房间管理与长对话

> Date: 2026-08-07
>
> Status: delivered and verified

## Background

V0.5 已经证明多房间创建、切换、URL 恢复和数据隔离，但房间只有名称且按创建
顺序排列。误写名称无法修正，停用房间无法收起，长对话在新消息到达时也可能
打断用户阅读。V0.6 只补齐日常使用所需的最小管理和时间线行为，不改首页、
Agent 协议或产品的信息架构。

## Delivered Scope

- 活动房间按最近一条已完成公开消息排序，并显示最长 160 字符的原文预览和时间。
- 房间 owner 可把名称修改为 1 至 80 字符；保存、成功和失败都有可见状态。
- 归档只改变房间状态，消息、运行、委派、Artifact 和成员关系全部保留。
- 归档最后一个活动房间会被拒绝；房间存在活动 Agent run 时也会被拒绝。
- 归档成功后切换到下一个活动房间；折叠的归档区可恢复原房间和全部历史。
- 初次打开和切换房间定位到最新消息。用户在底部附近时继续跟随；阅读旧消息时
  不抢滚动位置，并显示“回到最新消息”。
- 桌面保持二级房间栏，移动端保持抽屉；菜单、编辑、确认和恢复操作均可键盘使用。

## Key Decisions

1. 生命周期修改由服务端 owner 权限决定，浏览器状态不能授予权限。
2. 最后活动房间检查与状态修改共用 PostgreSQL advisory lock，避免并发归档绕过保护。
3. 最新消息预览是有边界的原文传输，不做语义摘要，避免 Yoyoo 越界承担 Agent 理解。
4. 时间线以距底部 120px 为跟随阈值；发送方乐观消息明确显示“发送中…”。
5. 恢复归档房间不强制跳转，避免打断当前工作上下文。

## Rejected Alternatives

- 硬删除：房间历史是可追溯工作记录，删除会扩大数据损失风险。
- 本版加入未读数：可靠未读需要成员级 read cursor 和 forward-only migration，移到 V0.7。
- 单独房间设置页：当前命令不足以支撑一个新页面，会增加导航和维护成本。
- 只做浏览器侧排序和保护：无法抵御并发请求，也不能作为权限边界。

- 影响范围：房间领域摘要、PostgreSQL room repository、协作服务、room API、
  浏览器 room client、对话页房间栏和时间线、相关测试与文档。
- 未改动：首页、Agent 请求协议、共享上下文规则、运行时依赖和数据库 schema。

  公开认证、通知、私聊和跨房间语义记忆。
