# 014 Feature: 多房间工作区

> Date: 2026-08-07
>
> Status: delivered and verified

## Background

V0.4 已经具备真实多 Agent、持久消息和共享房间上下文，但产品仍固定打开一个
初始房间，不同项目只能挤在同一条时间线里。V0.5 把现有多房间领域模型暴露成
最小可用 IM 工作区，同时冻结已经接受的首页，不提前引入完整团队管理。

## Delivered Scope

- 当前用户只能看到自己有成员关系的活动房间。
- 对话页可创建 1 至 80 字符的房间；同一幂等键只创建一次。
- 新房间在同一事务中加入创建者和当前工作区全部活动 Agent。
- 对话页可切换房间，当前房间写入 `?room=<uuid>`，刷新或打开链接可恢复。
- 未知或无权访问的房间 ID 回退到第一个可访问房间，不泄露房间数据。
- 房间切换时关闭旧 SSE 订阅并清空旧房间临时状态，消息、运行、委派、Artifact
  和 V0.4 Agent 上下文都继续以房间 ID 隔离。
- 桌面使用第二级房间栏，移动端使用抽屉；具备 loading、empty、error、creating
  和 ready 状态，并处理长名称截断与窄屏溢出。

## Key Decisions

1. 房间既是用户可见的 IM 上下文，也是服务端权限和数据隔离边界。
2. V0.5 创建房间时继承全部活动 Agent，避免第一版同时引入成员编辑器。
3. URL 只保存房间 ID，服务端仍执行成员检查；浏览器状态不能授予访问权限。
4. 房间创建使用调用方幂等键和事务级 advisory lock，重复提交不会产生重复房间。
5. 首页不承担房间列表或对话历史；多房间能力只进入 `/conversation`。
6. Playwright 使用生产构建、独立端口和每次运行唯一的 owner，验收数据不能进入正常本地工作区。

## Rejected Alternatives

- 同时重做首页：会把已冻结入口与 IM 基础能力绑在一次高风险视觉改动中。
- 第一版加入删除、改名、搜索、未读和通知：这些不是验证多房间隔离所需的最小能力。
- 仅在浏览器生成房间并稍后同步：无法保证成员、权限和幂等创建的一致性。
- 每个房间手动选择 Agent：会引入新的成员管理流程，推迟最核心的创建和切换闭环。
- 跨房间共享语义记忆：会破坏当前清晰的数据边界，并让平台承担 Agent 的理解职责。

- ESLint、TypeScript 和 Next.js 生产构建通过。
- 全量单元/UI：59/59 通过。
- 全量 PostgreSQL 集成：34/34 通过；5 个依赖真实外部系统的测试默认跳过。
- Playwright：18/18 通过，覆盖桌面与移动端首页回归、创建、切换、URL 恢复、
  消息隔离、移动抽屉、长名称、无横向溢出和既有多 Agent 协作流程。
- 人工视觉检查覆盖 `1440x900`、`390x844` 及移动房间抽屉；截图保存在
  `output/playwright/v0.5-desktop-room.png`、`v0.5-mobile-room.png` 和
  `v0.5-mobile-room-drawer.png`。

## Impact And Remaining Limits

- 影响范围：房间仓库与服务、当前工作区/房间 API、浏览器房间客户端、对话页和测试。
- 未改动：首页视觉、Agent 协议、V0.4 上下文规则、依赖和数据库迁移。
- 尚未实现：删除、归档、改名、搜索、置顶、未读、通知、自定义房间 Agent、
  多人邀请、公开认证、私聊和跨房间记忆。
