# 013 Feature: 多 AI 共享上下文

> Date: 2026-08-07
>
> Status: delivered and verified

## Background

V0.3 已证明 Codex 和 YOS 可以作为两个真实 Agent 同处一个持久房间，但每个
运行仍只收到当前消息，无法接住另一个 Agent 之前说过的事实。V0.4 的目标不是
给 Yoyoo 增加一个中心 Brain，而是让所有 Agent 获得同一份可审计的公共房间
事实，从而形成真实多轮协作。

## Delivered Scope

- 通用房间请求新增严格类型的 `history`，同时保留当前触发消息为独立字段。
- 只读取同一房间、状态为 `completed`、且严格早于触发消息的公开消息。
- 最多 24 条、总计 16,000 字符、单条最多 8,000 字符；截取后仍按时间正序。
- 同一触发消息并行启动的多个 Agent 使用相同历史边界，不能看到彼此当前轮回复。
- Codex 和 YOS 使用相同通用上下文，由各自适配器序列化，不向领域模型加入厂商字段。
- 重试继续围绕原始触发消息重建上下文，因此不会因为重试时间不同而漂移。

## Key Decisions

1. Yoyoo 只负责房间隔离、顺序、边界、限制和传输；理解、记忆、推理与回复仍属于 Agent。
2. 历史在适配器提示中标记为不可信参与者内容，并与当前消息使用独立定界区。
3. 上下文从权威 PostgreSQL 消息记录构建，不从浏览器状态、供应商会话或隐藏缓存构建。
4. 子运行终态与对应委派终态在同一数据库事务提交，避免快照出现已完成运行配运行中委派。
5. 取消先确认活动运行并触发 abort，之后才写干预消息；已终态运行拒绝迟到取消。

## Rejected Alternatives

- 向量数据库、语义检索和自动摘要：当前房间历史很小，引入后会让 Yoyoo 开始解释内容，超出平台边界。
- 为 Codex、YOS 各写一套历史查询：会产生不同过滤规则，破坏多 Agent 看到同一事实的原则。
- 使用持久供应商会话：不可审计、不可移植，也无法保证重试与并行触发的一致边界。
- 只增加等待时间修复委派测试：失败来自两个事务之间的真实不一致窗口，不是测试太快。
- 终态取消仍返回成功：会留下虚假干预消息和永久“正在停止”状态，因此拒绝。

## Verification Evidence

- 目标单元测试：27/27 通过。
- 仓库与上下文边界测试：4/4 通过。
- 全量单元/UI：56/56 通过。
- 全量 PostgreSQL 集成：30/30 通过；5 个真实外部测试默认跳过。
- ESLint、TypeScript 和 Next.js 生产构建通过。
- Playwright：16/16 通过，覆盖桌面与移动端首页、房间、刷新恢复、干预和溢出。
- 显式真实 Codex/YOS 联调：1/1 通过，耗时 378.77 秒；完成双向未知标记接力、并行回复和运行时重开恢复。

## Impact And Remaining Limits

- 影响范围：房间 Agent 请求、Codex/YOS 提示边界、运行上下文数据库查询、委派终态一致性和取消语义。
- 未改动：首页、房间视觉、数据库迁移、依赖、语音、认证和多用户界面。
- 尚未实现：跨房间记忆、语义记忆、历史配置 UI、文件上下文、第三个真实外部 Agent。
